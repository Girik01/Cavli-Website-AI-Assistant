Cavli Website AI Assistant – technical note

Assignment 1 · Website AI Assistant & Product Discovery · working prototype, local run · model: gpt-5.4-mini + text-embedding-3-small · vector store: Qdrant Cloud

1. What it is, and what it is not

A small chat assistant that answers questions about Cavli cellular IoT modules from 26 public cavliwireless.com pages (7 category pages, 19 module pages; two modules are the demo focus: C16QS and CQM220). Every factual answer carries clickable source links. When the sources do not support an answer, it says “Not verified in available sources” and shows a relevant page and the Contact link.

Scope decision: this is deliberately a simple, single-question chatbot. Each question is answered on its own; there is no conversation memory, no agent and no tool use. This keeps behaviour predictable, easy to test and cheap. A follow-up such as “what about its price?” is not understood without the module name.

3. Retrieval

  • Sources: 26 pages, listed with URL, fetch date and chunk count in 01_sources.md. Hardware and AT manuals need a login, so they are not used (questions about them get the standard “not verified” reply).
  • Chunking: one chunk per page section (About, Key Highlights, Bands per region, GNSS + OS, Speeds, Packaging, Interfaces, Use Cases, Variants, each FAQ question). Comparison tables are never split and every cell keeps its product name. Each chunk starts with a header such as [Product: C16QS | Category: LTE Cat 1bis | Section: Bands – Europe], which is what lets a question that names a module find that module's chunk without any metadata filter.
  • Search: the question is embedded once and Qdrant returns the 12 closest chunks (cosine). No query rewriting, so there is no extra model call. Chunks below 0.30 are dropped; if even the best chunk is below 0.35 the question is treated as off-topic.
  • Why dense only: I compared dense search with hybrid (dense + BM25) on 351 frozen questions (templated spec questions plus a paraphrase of every FAQ). Pass rate with the needed chunk in the top 8: dense 96.6%, hybrid 92.9%, BM25 alone 69.2%. The header repeats the module name on every chunk, which makes keyword scores match “any chunk of that module” instead of the chunk holding the fact.
  • Caveat: that question set is generated from the same chunks, so it is friendlier than real traffic, and it measures retrieval only. A hand-written blind set should be added before quoting the numbers outside this assessment.

4. Answers, citations and “supported vs inferred”

  • The model may use only the retrieved chunks and must end each factual sentence with the id of the supporting chunk. The server turns ids into numbered links to the exact page ([1] → the module page, with the section name shown on the source chip).
  • Citation checks: (a) a cited id must be one of the retrieved chunks; (b) every number in the answer must appear in a cited chunk (if it only appears in another retrieved chunk, that chunk is added as a citation; if nowhere, the answer is replaced by the “not verified” reply); (c) if the question names modules, cited chunks must belong to those modules.
  • Supported vs inference: facts carry citations. Judgement (for example why a module fits a smart meter) goes in a separate Inference box labelled “not stated in the sources”. Requirements the sources do not confirm (cost, battery life) are listed under Not verified in sources. For vague selection questions the model asks a clarifying question instead of naming a winner.
  • Conflicts: where the site contradicts itself, both values are kept and reported with their source, never merged. Found by automatic comparison: 14 cases, e.g. CQM220 peak speed (220/120 Mbps on the module page vs 226 and 195/105 Mbps in category text), CQS315 eSIM (“Integrated eSIM” in highlights, but both listed variants say “eSIM: No”), CQS315 shows a “5G RedCap” badge on an LTE Cat 4 page, CQ16 bands and SIM count differing between its page and the comparison table.
  • Unsupported questions: the standard reply is “Not verified in available sources…” plus the closest module page and the Contact link. Price, stock and lead time are answered by rule with the same wording (they are never public); if such a question also asks for something answerable (“bands and price”), the answerable part is answered and the price is flagged as not verified.

6. Security, privacy, latency, feedback, failures

  • API-key security: OpenAI and Qdrant keys exist only in the server's .env (git-ignored; .env.example has empty names). The browser calls only /api/*. No key appears in the code, logs, test outputs or the submitted package (scanned).
  • Privacy: no accounts or cookies; the log stores a random request id, the question text with personal data removed, response type and timings. Questions go to OpenAI to be answered (state this in the site's privacy text).
  • Latency is measured per request (retrieval, first word, model, total), shown under each answer, logged and summarised at /api/metrics. On this run (20 requests, local server calling Qdrant Cloud and OpenAI): average 3.3 s, median 3.5 s, p95 5.9 s; the first words appear after about 2.5 s because text streams while the answer is still being written. Rule-based replies take about 10 ms.
  • Feedback loop: thumbs up / down under each answer → POST /api/feedback → data/feedback.jsonl with the request id, so a bad answer can be traced to its question, chunks and timings.
  • Failure handling: backend or model errors return a friendly message with the Contact link (no stack traces, no keys); if the server is unreachable the widget shows “Could not reach the assistant”. Setup is reproducible: uv sync, copy .env.example, uv run python -m ingest.build26 --upsert, uv run app/main.py.

8. Assumptions, costs, simulated parts and limitations

  • Services and models: OpenAI gpt-5.4-mini (reasoning off) and text-embedding-3-small; Qdrant Cloud. Per question: 1 embedding call + 1 chat call with 12 chunks (roughly 2–4k input tokens, my estimate). Cost per question was not measured; check current OpenAI pricing before planning volume.
  • Implemented, not simulated: ingestion, retrieval, streaming answers, citations, guardrails, feedback, metrics, embeddable widget. Not built: login, analytics dashboard, scheduled refresh (the command exists, the scheduler does not), production hosting.
  • Limits: single-turn only (by design); list questions (“which modules support band 71?”) see only 12 chunks and may be incomplete; rare-keyword selection (“Wi-Fi 6 and Bluetooth 5.4”) can miss under dense-only retrieval; the answer wording can vary between runs, so a source conflict is occasionally left out (4 of 4 runs reported it after the last prompt fix, earlier 2 of 4); brochures, blogs and login-only manuals are not indexed; the site's own pages contradict each other in places (kept visible, not resolved); the quality judge for generated answers is the same model family, so it was not used as proof of accuracy.
